# 高通量任务执行框架

## 设计原则

1. **队列驱动**：任务列表 → 顺序执行 → 验证 → 记录 → 下一个
2. **不阻塞**：外部 API 限流时立即切换，不等待
3. **强制复测**：每个任务必须有验证步骤
4. **心跳降级**：后台维护，不打断主执行流

## 任务粒度

| 类型 | 时长 | 命令数 | 示例 |
|------|------|--------|------|
| 轻量 | ≤5 min | ~15 cmd | 搜索/评论/写文件 |
| 中等 | ≤15 min | ~30 cmd | capsule 生成+发布 |
| 重型 | ≤30 min | ~60 cmd | 代码修复+测试 |

## 执行流程

```
┌─────────┐    ┌──────────┐    ┌──────────┐    ┌─────────┐
│ 取任务   │ →  │ 执行任务  │ →  │ 验证结果  │ →  │ 记录日志 │
└─────────┘    └──────────┘    └──────────┘    └─────────┘
     ↑                                                  │
     └──────────────────────────────────────────────────┘
                              ↓
                        验证失败 → 修复重试
```

## 验证规则

| 任务类型 | 验证方法 |
|----------|----------|
| 写文件 | `cat <file> \| head -5` 确认存在且内容正确 |
| API 调用 | 检查 HTTP 状态码和返回体 |
| 代码修改 | 运行测试或 dry-run |
| Git commit | `git log -1` 确认 commit 存在 |
| EvoMap 发布 | 检查返回的 bundle_id 或 auto_promoted |

## 限流处理

1. 第 1 次失败：等待 10 秒，重试
2. 第 2 次失败：保存 pending，切换任务
3. 不尝试第 3 次

## 产能指标

- 理论日产能：7200 cmd ÷ 20 cmd/任务 = 360 个
- 实际目标：100 个/日（含验证和记录）
- 有效利用率：100/360 ≈ 28%
